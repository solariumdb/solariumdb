# Differences from RocksDB

RocksDB is the reference behavior: a deliberate difference is listed here, and an accidental one is a bug. The RocksDB behavior these documents describe is checked against RocksDB 11.8.1. The `Kommander.RocksDB` package that the benchmarks run (11.8.1.9002) carries a native library built from that release.

- The manifest is rewritten whole on each change. RocksDB appends edits to a log.
- A data block stores each key whole, after 17 bytes of lengths, sequence number and kind. RocksDB stores only the part of a key that differs from the key before it, with varint lengths.
- `ColumnFamilyOptions.Compression` defaults to `None`, and its only codec is LZ4 (`Lz4`), from the managed `K4os.Compression.LZ4`; RocksDB's default is Snappy, and it offers more codecs. Only data blocks are compressed; RocksDB never compresses filter blocks, and compresses index blocks only to keep them in its block cache. As in RocksDB, a block that compression shrinks by less than an eighth is stored raw. With `CacheDataBlocks`, a compressed block is decompressed once per cache miss, as in RocksDB; without it, Solarium's default (below), every read of it decompresses it. Kommander's log keys share their first 25 of 31 bytes, so with 256-byte values and no compression in either engine, Solarium's flushes wrote 8% more bytes than the keys and values, and RocksDB's 4% fewer.
- A family has no block cache unless `ColumnFamilyOptions.BlockCache` is set; RocksDB gives a table factory without one an LRU cache of its own, 32 MiB in current releases. The cache holds the index and filter blocks with `CacheIndexAndFilterBlocks`, and the data blocks only with `CacheDataBlocks`, which RocksDB has no switch for: it caches data blocks whenever it has a block cache. Without it, every read of a data block reads it from the file, through the OS page cache. Caching them made reads 11% to 20% faster from one thread on a store that fits in the cache, but from 8 threads, or on a store ten times the cache, 0.5 to 0.8 times as fast: each lookup takes a shard's lock, and each cached block was then an array the garbage collector had to copy and free once evicted (see [benchmarks.md](benchmarks.md)). A data block is cached decompressed, in native memory charged its length, with a small managed handle that counts its readers, so an eviction frees it once the last reader releases it; RocksDB charges a block's allocation and its handle. The data blocks of a table that a compaction retires stay in the cache until it evicts them, as in RocksDB, but its index and filter partitions are erased at once; a database that closes erases all of its entries, which RocksDB leaves to the LRU. The cache's high-priority pool (`highPriorityPoolRatio`, RocksDB's `high_pri_pool_ratio`, 0.5 by default as in RocksDB) takes the index and filter blocks (`CacheIndexAndFilterBlocksWithHighPriority`) and every entry read again since its insert, as RocksDB's LRU cache does; there is no low-priority pool ratio and no bottom priority, which RocksDB uses for blobs.
- Every table has a partitioned index and filter, as RocksDB's `index_type = kTwoLevelIndexSearch` with `partition_filters`, which RocksDB writes only when asked: partitions of 4 KB of index entries (`metadata_block_size`), each with a filter on the user keys of its blocks, under a top-level index. The top-level index stays in the reader, counted in `estimate-table-readers-mem`; RocksDB caches it, pinned by `pin_top_level_index_and_filter`. A partition's index and filter are one cache entry, charged the bytes of their arrays; RocksDB caches them as two blocks, charged their allocations. A table reads every partition at open, verifies it, and caches it, as RocksDB with `prefetch_index_and_filter_in_cache`; a table that a compaction writes caches its own at open too. A lookup on a partition that the cache evicted reads its two blocks again from the file and decodes them, a few kilobytes, where RocksDB searches a block in place: with a cache of a quarter of the partitions, lookups from one thread ran about 2.5 times slower than with all of them (see [benchmarks.md](benchmarks.md)). A table written before partitions has one partition, its whole index and filter, until a compaction rewrites it.
- `CacheIndexAndFilterBlocks` without a `BlockCache` throws. RocksDB gives a table factory with no block cache a cache of its own (above). There is no strict capacity (`strict_capacity_limit`): the cache stays over its capacity when only pinned entries are left, as RocksDB's default. A read keeps the index it took after the cache evicts it, without holding a reference that keeps it in the cache: an evicted entry's charge leaves the cache at once, and its memory when the last reader drops it. An iterator keeps the index partition of each table it reads until it moves to another partition or is disposed, as RocksDB's iterators keep the index block they read. Compactions read their inputs with `fill_cache` off, as RocksDB's.
- Levels are always sized dynamically, as RocksDB's default `level_compaction_dynamic_level_bytes`; there is no option for static targets from level 1 down. A family that shrank keeps its base level at the first level with files, as RocksDB does, but its levels above the size it needs are not drained: RocksDB compacts such a level down on its own.
- Level 0's score is its file count only. RocksDB, with dynamic level sizing, also scores level 0 by its bytes against the base level's target, so a few large level 0 files compact sooner. Scores do not discount the bytes that compactions are about to bring into a level, as RocksDB's do.
- A merge runs on one thread: there are no subcompactions (`max_subcompactions`, whose default is 1), which split a large merge into key ranges on several threads.
- A level 0 merge picks the oldest file first, as RocksDB does; a merge of a sorted level takes one file chosen by `kMinOverlappingRatio`, with no expansion to more files of the level, and without RocksDB's checks of the overlap two levels down (`max_compaction_bytes`, the grandparent overlap). A move from level 0 is allowed for several files at once; RocksDB moves several level 0 files only into a level that has files, and one file into any level.
- A range tombstone is cut at the boundaries between a merge's output files with a user key as the bound, excluded, which the table records; RocksDB bounds files with internal keys and a sentinel.
- A merge keeps the sequence numbers of the entries it writes. RocksDB sets them to 0 in the bottom level.
- `CompactRange` does not flush a memtable that overlaps the range first.
- `CreateCheckpoint` links the SSTables, as RocksDB does, and copies them when the file system refuses the first link (another file system, or one without hard links), as RocksDB does after its first `NotSupported`. The checkpoint holds no WAL file: what the memtables hold at the checkpoint's sequence number goes to new SSTables of the copy, and the source is not flushed. RocksDB copies its WAL files into the checkpoint while their total is below `log_size_for_flush`, and flushes the source's memtables otherwise. The `FORMAT` file is written last, so a checkpoint cut short does not open; RocksDB builds the checkpoint in a `.tmp` directory and renames it. The checkpoint holds its directory's `LOCK` while it writes, and the copy keeps the `LOCK` file. `Dispose` stops a running checkpoint and waits for it; with RocksDB, closing the database during a checkpoint is the caller's error.
- Compactions run on up to `MaxBackgroundCompactions` threads, and flushes on one; there is no `max_background_jobs` to split between them, and no `max_background_flushes`. A manual compaction is always exclusive (`exclusive_manual_compaction`, RocksDB's default).
- The `RateLimiter` paces writes only, as RocksDB's default mode `kWritesOnly`; there is no `kReadsOnly` or `kAllIo`, and no `rate_limiter_priority` on reads or on `WriteOptions`. A replay's flushes inside `Open` are not paced; RocksDB's recovery flushes go through the limiter. Fairness serves the compactions first on every tenth refill, where RocksDB draws it at random, one in ten. There is no `wal_bytes_per_sync`: the WAL syncs whole groups.
- The delayed write rate is fixed. RocksDB adapts it while writes are delayed: it lowers the rate as the compaction backlog grows and near the stop trigger, and raises it as the backlog shrinks. There is no stall on pending compaction bytes (`soft_pending_compaction_bytes_limit`, 64 GB): only the level 0 file count slows and stops writes. There is no `WriteOptions.no_slowdown`, which fails a write instead of delaying it.
- A `WriteBufferManager` counts the memtables as `cur-size-all-mem-tables` does (below), not the arena blocks they allocate. It never stalls writes (`allow_stall`). With a cache, it charges the memtables to it in pinned entries of 256 KiB, as RocksDB's `CacheReservationManager`, and gives them back as soon as the memory falls, where RocksDB keeps them until it falls below three quarters of the reservation. Each write group's memtable bytes are charged after its inserts, so while commits are pipelined, the check before a group can trail by the groups still in their memtable stage. Replay charges what it inserts and flushes only at `WriteBufferSize`, as RocksDB's recovery, so the first write after an open past the cap flushes. A memtable's bytes leave the manager when its flush installs its table, even while readers of older versions still hold it; RocksDB frees them when the last reference to the memtable goes. Its native memory goes, as in RocksDB, with the last version or flush that holds the memtable.
- `Flush` does not wait for a stall to clear first. RocksDB's `Flush` (`FlushOptions.allow_write_stall` false, the default) waits while one more level 0 file or memtable would delay or stop writes.
- `Level0FileNumCompactionTrigger` or `TargetFileSizeBase` below 1, a slowdown trigger below the compaction trigger, a stop trigger below the slowdown trigger, or a `DelayedWriteRate` below 1 throws. RocksDB raises a trigger of 0 to 1 and each later trigger to the one before it, with a warning in its log, and takes a `delayed_write_rate` of 0 as 16 MiB/s.
- Each WAL record carries the offset of the file that a flush had made durable, and recovery uses it to tell power-loss damage from damage to flushed data; RocksDB's WAL has no such field, so its recovery modes either fail the open after such a power loss or drop data after any damage. The WAL file has a header of its own and a version, not RocksDB's 32 KB blocks.
- The memtable indexes its range tombstones in runs of fragments that the range delete builds, in sizes that double, and a read searches each run (see [design.md](design.md)). RocksDB caches the fragments of all of a memtable's range tombstones, which the first read after each range delete builds again, so that read pays for all of them; here a range delete pays, at most once each time the count of tombstones doubles, and a read searches up to one run per doubling.
- `cur-size-all-mem-tables` counts the nodes of each memtable in its native arena, each its key, its value, a 24-byte header and 8 bytes per skip-list level, rounded up to 8, and its range tombstones with their fragments, so an empty memtable is 0; RocksDB counts the arena blocks it allocated, 2 KB for an empty one. The arena's 64 KiB chunks hold, besides, at most one partly filled chunk per processor that wrote to the memtable. `estimate-table-readers-mem` counts the index keys and handles, the filter bits, and the range tombstones and their fragments of each open table, not its allocations; with `CacheIndexAndFilterBlocks`, the range tombstones and their fragments only, as RocksDB's leaves out the cached blocks.
- `Dispose` flushes the current WAL file before it closes it, so every write before a clean close survives a power loss after it. RocksDB's close, with the WAL on, writes the WAL to the OS without a flush (unless it uses direct I/O) and flushes no memtable, so its unsynced writes need `SyncWAL` first. A flush that fails at `Dispose` is reported after the close completes.
- `MultiGet` reads the data blocks of a round in one `IStorageEnvironment.MultiRead`, across every table the round reaches, and has no `async_io` or `optimize_multiget_for_io` option. RocksDB's `MultiGet` reads the blocks of one table with one `MultiRead` of its file. The io_uring environment's `MultiRead` reads what the page cache holds on the calling thread first, with `preadv2(RWF_NOWAIT)`, and sends only the rest to the ring; RocksDB's `PosixRandomAccessFile::MultiRead` submits every read to its io_uring.
- `Prev` searches every source for each step, so it is slower than `Next`.
- After `Flush`, the WAL file changes at the next write group, not at once.
- Commits are pipelined by default; RocksDB's `enable_pipelined_write` is off by default. In the `Put` benchmarks ([benchmarks.md](benchmarks.md)), pipelining makes 3 to 16 unsynced writers 5% to 15% faster, and 16 writers beside 16 readers 11% faster, and costs a single writer 1.5% to 1.7%. At 2 writers the result changes with the build, from 8% faster to 7% slower. Because a group gives up its leadership after its WAL append, the next group can prepare before this one's entries are in the memtable, so a full memtable is switched one group later than without pipelining, as in RocksDB.
- In a group of several writers, the leader launches the inserts of the members that still spin and inserts the batches of the blocked ones itself; RocksDB launches every member. A blocked member must wake and get a CPU before it can insert, so a launch puts its wake before the publication of the group, and where most waiting writers block, as on io_uring or beside readers, that made writes up to 2.8 times slower (5.5 times beside 16 readers) than inserts by the leader alone. Kept, the member wakes after the publication. The leader waits for the last insert and publishes the group. In RocksDB, the last writer to finish its insert publishes the group and ends it. Solarium's leader holds the lock that keeps `Flush` from switching a memtable during the inserts, and that lock belongs to its thread; RocksDB's `Flush` waits in the write queue instead. RocksDB's leader wakes the writers of a group of 20 or more through about √n of them; Solarium's leader wakes each one. Concurrent range deletions go to a copy-on-write array under a small lock, not to a second skip list.
- A writer that waits for its group spins for up to 20 µs before it blocks, or for 1 µs when probes show that more than about a quarter of the long spins end in a block. A writer that waits for a WAL flush does not spin. RocksDB's writers spin for about 1 µs (200 pause loops). Then, with `enable_write_thread_adaptive_yield` (on by default), they call `sched_yield` for up to `write_thread_max_yield_usec` (default 100 µs), and block after 3 yields that each take `write_thread_slow_yield_usec` (default 3 µs) or more. A credit, updated on one wait in 256, decides whether a writer yields at all. Solarium has no yields: in the `Put` benchmarks, yields after 1 µs or 5 µs made 16 writers on 16 CPUs 8% to 10% slower than a spin without yields. It keeps RocksDB's sampled credit, with the same decay of 1/1024, but the credit chooses between a spin of 20 µs and one of 1 µs, and it stops the long spin when more than about a quarter of the probes block, not half. While the spin is short, Solarium probes in windows of long spins, not one wait at a time as RocksDB does: on macOS (8 CPUs, 16 writers), single probes among short spins blocked 45% of the time where a fixed 20 µs spin blocked 3%, so the spin stayed short, and each `Put` took about twice as long. RocksDB's credit starts at 0, so one early block stops its yields; Solarium's starts 16 blocks above 0, because on Linux, with six writers on one thread per core on io_uring, a credit that started at 0 made 28% to 38% of the turns spin short where a fixed 20 µs spin blocked on 12%. In the benchmarks, the long spin was faster where 13% or fewer of its spins blocked, and slower where 40% or more blocked: on io_uring with 16 writers on 16 CPUs (36% slower than 1 µs), and with six writers on three cores and their hyperthreads (30% slower). RocksDB does not check for a flush. With 16 readers beside 16 writers on 16 CPUs, the long spin costs the readers about 8% of their `Get`s. Only 2% of its spins block there, so the credit keeps it.
