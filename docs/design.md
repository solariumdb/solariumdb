# Design

How Solarium is built: the column families, the write path (group commit), the lock-free read path, flushes, compactions and write stalls, the SSTables, and the files in the data directory. The WAL and recovery have their own document, [durability.md](durability.md), and so do the storage environments, [storage-environments.md](storage-environments.md). Where Solarium departs from RocksDB on purpose, [rocksdb-differences.md](rocksdb-differences.md) says so.

## Column families

A column family is a named, ordered key space. All column families share the WAL and one sequence of sequence numbers. That is what makes a batch across column families atomic.

Each column family has a **version**, like RocksDB's `SuperVersion`: the active memtable, the immutable memtables that wait for a flush, and the SSTables. A version never changes after it is published. A memtable switch or a finished flush publishes a new one.

## Writes: group commit

1. A writer encodes its batch into a WAL record, all but the sequence numbers, and notes the column families the batch writes to. Then it joins the write queue. When no leader is active, it becomes the leader.
2. The leader takes the queue as its group, from the front, up to `MaxWriteBatchGroupSizeBytes` of records, with RocksDB's rule for `max_write_batch_group_size_bytes`: when the leader's own batch is at most an eighth of the cap, the group stops at the leader's size plus an eighth. The leader's batch always goes, so a larger batch is a group of its own. The writers left in the queue wait for the offer of leadership at the end of the group. After a group larger than twice the cap, the leader's record buffer is replaced, so one large batch does not keep its memory.
3. The leader switches every full memtable of the families that the group writes to, and, when the `WriteBufferManager` is past its cap, the database's memtable with the oldest data (see Flushes).
4. The leader copies the writers' records into one buffer, gives each its first sequence number and its checksum, and writes them to the WAL in one append. RocksDB's leader also concatenates batches that its writers encoded. If any writer asked for `Sync`, it flushes the WAL once.
5. The leader offers leadership to the oldest writer in the queue, if there is one, so the next group's WAL append runs while this group goes into the memtables. This is RocksDB's `enable_pipelined_write`.
6. The group waits for its memtable stage. One stage runs at a time. A group that finds none running starts one at once; otherwise it joins a memtable queue, in WAL order, and its leader waits, as a writer in the write queue does. When a stage ends, it offers the next stage to the leader of the oldest group in the queue, and that stage takes every group in the queue, as RocksDB's memtable writer groups.
7. The batches of the stage go into the active memtables, each operation under the sequence number that its WAL record has. In a stage of several writers, its leader tells every other writer that still spins to insert its own batch, inserts its own and those of the writers that blocked, and waits for the last insert, as RocksDB's `allow_concurrent_memtable_write` does. The leader of a stage of one writer inserts its batch alone.
8. The stage's leader publishes the last sequence number of the stage. This makes its groups visible at once, and groups become visible in WAL order. Then it completes each writer of the stage.

With pipelining off (an internal option, so the tests can run both paths), the leader inserts and publishes its group before it offers leadership, and the next group starts only then.

A writer in the queue waits on its own signal, as in RocksDB. The end of a group wakes only the writers of the group and the oldest writer in the queue, and a writer of the group returns without the queue's lock. A waiting writer spins for up to 20 µs before it blocks, so it seldom needs a thread wake. The spin adapts to how earlier spins ended. While the spin is long, one turn of a waiting writer in 256 is a probe: it spins for the whole 20 µs, and its outcome, in time or a block, updates a credit that the database keeps. While at most about a quarter of the probes block, every turn spins for 20 µs. When more block, the other turns spin for 1 µs only, because a long spin then holds a CPU that the leader, its hyperthread sibling or the storage environment's I/O thread needs, and the writer blocks anyway. While the spin is short, a single probe would wait for the wakes of the writers that blocked before it, and block more often than a long spin among long spins. So the probes run in windows: once in 8,192 turns, 256 turns spin for 20 µs, and the last 128 of them are probes. The long spin comes back when it ends in time again, and its probes then go on at once, one turn in 256. A new database starts with the long spin and a margin of credit: 16 probes that block in a row make the spin short, so a block in the first groups does not. A writer that waits for a WAL flush blocks at once, because the flush takes far longer than the spin: it waits behind a group that syncs, or it is in a next group that syncs and does not lead it.

Each writer of a group reads its own batch from its own core's cache, and the inserts no longer run one at a time on the leader's path. The stage's leader holds the lock that a memtable switch takes from the inserts to the publication, so a `Flush` cannot switch a memtable while writers fill it. A WAL file stops being current only after every group appended to it has been published, so a flush never deletes a WAL file whose data is not in a memtable yet. A writer that finished its insert waits for the publication with the long spin: the wait holds no I/O, only the other inserts. If an insert fails, the group fails, and the database refuses all writes until it is opened again, as after a WAL failure: the WAL holds the whole group, and part of it is in the memtables under sequence numbers that were never published.

The offer of leadership is not a hand-off, unlike in RocksDB. A writer that arrives while no leader is active takes the queue and leads it, and the writer that got the offer then waits for that group. A running writer starts the next group sooner than a blocked one can wake up. The leader makes the offer under the write lock, while the writer is still the oldest in the queue, and wakes it after the release; an offer made after the release could reach a writer that has left the queue since, and that waits for its own memtable stage, where it would read the offer as the offer of that stage.

A write that is not synced survives a process crash, but not a power loss. This is the same as in RocksDB. After a clean close it survives a power loss too: `Dispose` flushes the current WAL file.

## Reads: no locks

A read takes the column family's version, then the last published sequence number as its snapshot, in that order, as in RocksDB. A version never loses data that its own snapshot can see, but a newer version may. The snapshot can be newer than the version's memtables. A memtable switch splits the sequence numbers at one point, so the read still sees the whole state at one sequence number.

A read searches the version's sources newest first: the memtables, the SSTables of level 0, newest first, and then each of levels 1 to 6 that has files, whose files are in key order and do not overlap, as one source per level. Within one column family, for each key, every version of the key and every range tombstone covering it in a newer source has a higher sequence number than every one in an older source. So the first source with a version of a key decides the result.

`MultiGet` reads in rounds, as RocksDB's batched `MultiGet`, over batches of up to 32 keys. A round searches each key's sources from where it stopped, until a memtable answers or a table's index names the data block that would hold the key; then it reads the distinct blocks of the round, which keys often share, in one `IStorageEnvironment.MultiRead`, and settles each key its block has a version of. A key whose block has none, after a Bloom filter's false positive, goes on to the next source in the next round. Most calls take one round. On io_uring, the reads that the page cache misses are in flight together, so the drive serves them at once.

A reader counts itself into the version it reads, and out when it is done; an iterator does so when it is disposed. A table stays open until the last version that lists it has no readers and has been replaced. The counts are kept per CPU, so readers on different CPUs do not share a cache line.

The memtable is a multi-version skip list with readers that take no lock, the LevelDB design, and either one writer or the writers of one group at once. A concurrent insert links each level of its node with a compare-and-swap, from the bottom level up, and searches only that level again when a link changed under it, as RocksDB's `InlineSkipList::InsertConcurrently` does. An SSTable is immutable. An iterator merges one cursor for each source and keeps the snapshot and the version of its creation, so a later flush does not change what it sees. It keeps that version's SSTables open until it is disposed.

A range tombstone (from `DeleteRange`) hides every older version of the keys in its range, in every older source. Each source finds the tombstones over a key as RocksDB's `FragmentedRangeTombstoneList` does: its tombstones are cut at every begin and end into fragments that do not overlap, each with the sequence numbers of the tombstones over it, and a read binary-searches the fragment of its key, then the highest sequence number at or below its snapshot. A table builds its fragments when it opens; up to 8 tombstones, it scans them instead, which costs less than the build. The memtable's tombstones change with each range delete, so its writer indexes them in runs: when 8 tombstones are past the last run, it builds them into a run, together with the runs before it that are no larger, as a binary counter carries. The runs are 8, 16, 32 and more tombstones, one of each size at most, and a lookup searches each run and scans the fewer than 8 tombstones past the last, so no reader builds anything. Each tombstone takes part in one build each time the count of tombstones doubles; the largest build, of all of them, falls on the range delete that makes the count 8 times a power of two, and the runs' fragments count in the memtable's size. RocksDB caches the fragments of all of a memtable's tombstones until the next range delete, so the first read after each one fragments them all again.

## Flushes

1. A memtable that reaches `WriteBufferSize` becomes immutable at the next write group. `Flush` does the same at once.
2. A background thread writes the oldest immutable memtable to an SSTable and flushes the file. As in RocksDB's flush with no snapshot, it writes only the newest version of each key, and drops a key that a newer range tombstone of the same memtable covers; the range tombstones stay, and so does a point delete that no tombstone covers, because they hide data in older tables. A reader that enters the version with the new table takes its snapshot after the table is installed, above every entry of the memtable, so it needs nothing that was dropped; a reader of the older version reads the memtable itself. This keeps the entries that die while still in memory, such as Kommander's log rows under a confined tombstone, out of the SSTables.
3. The current WAL file is flushed, so no record before the table can be lost while the table survives. A batch can span families, and the rest of it, or an earlier batch of another family, may still be in the WAL alone; a power loss would otherwise keep the table and lose them. RocksDB syncs its closed WAL files before it commits a flush for the same reason. The older WAL files were flushed when they stopped being current.
4. One manifest save records the table and the new flush point of the family, and drops the WAL files that no memtable needs.
5. A new version replaces the memtable with the table. Then the dropped WAL files are deleted.

When a family holds `MaxWriteBufferNumber` memtables, writes wait for a flush. When the live WAL files are larger than `MaxTotalWalSize`, the families that keep the oldest WAL file alive are flushed. That stops a family with few writes from keeping old WAL files forever.

A `WriteBufferManager` caps the memtables of every database that shares it, as RocksDB's. After the inserts of each write group and before its publication, the stage's leader charges the bytes that the group added to each active memtable, once per group and not per entry. A switch moves a memtable's bytes out of the manager's active memory, and the flush's install, or the close, takes them out of its total. Before each group, the leader asks the manager, as RocksDB's `ShouldFlush`, whether the active memtables of all the databases hold more than 7/8 of the cap, or all memtables reach the cap with half of it active; if so, it switches the column family of its own database whose active memtable holds the oldest data, as RocksDB's `HandleWriteBufferManagerFlush`. A database never flushes another's memtables, so the memory of a database that takes no writes stays until it does.

A flush failure, like a WAL failure, stops all later writes until the database is opened again. Reads continue.

## Compactions

A column family has RocksDB's seven levels: level 0, whose files are flushed memtables and can overlap, newest first, and levels 1 to 6, whose files are each in key order and share no key within the level. For each key, every version in a level is newer than every version in the levels below it.

The levels are sized as RocksDB's `level_compaction_dynamic_level_bytes`, its default. Level 6, the bottom level, holds what it holds, and each level above it has a target of a `MaxBytesForLevelMultiplier`th (10) of the one below. Level 0 compacts into the base level: the highest level whose target is still at most `MaxBytesForLevelBase` (256 MB), and never below the first level with files, so the levels above the base level are empty. `LevelTargets` computes this as RocksDB's `VersionStorageInfo::CalculateBaseBytes`. A family below `MaxBytesForLevelBase` therefore keeps its sorted data in level 6, and level 0 compacts straight into it. At 4.3 GB in level 6, the targets are 430 MB for level 5 and 256 MB for level 4, the base level.

Up to `MaxBackgroundCompactions` compactions run at once, across all families, each on a thread of its own (default 1, RocksDB's `max_background_compactions` of its default 2 background jobs). Each family's levels have a score, as RocksDB's: level 0's file count over `Level0FileNumCompactionTrigger`, and for each level from the base level to level 5, its bytes over its target. The level with the highest score of at least 1, across the families, goes first.

1. **Level 0 into the base level.** From the oldest level 0 file, the files that overlap neither each other nor a file of the base level move there as they are: one manifest save changes their level, and they keep their numbers. The first file that overlaps ends the walk, so every file that stays in level 0 is newer than every file that moves. Otherwise the oldest file, every level 0 file that overlaps it (and the ones that overlap those), and the base level's files in their range are merged into new files of the base level.
2. **A sorted level into the one below.** One file, the one whose overlap in the level below is smallest against its own size (RocksDB's default, `kMinOverlappingRatio`), with every file of the level below that it overlaps. A file that overlaps nothing there moves down as it is. This is how an append-only key space, such as a Raft log, reaches level 6 with no rewrite.
3. **The merge.** Every version of a key in the levels a merge reads is an input, so it keeps only the newest version of each key, and only when no range tombstone of the inputs covers it. Below the output level, older versions can still exist. A point delete is kept while a file of a level below holds its key, as RocksDB's `KeyNotExistsBeyondOutputLevel` asks, and a range tombstone while a file below overlaps it, so a merge into level 6 drops them all. A kept range tombstone is cut at the boundaries between the output files, as RocksDB truncates them, so each file's key range covers its tombstones. The cut piece of a file ends at the next file's first key, which then is the file's largest bound, excluded: a table records when its largest bound is a tombstone's end that none of its entries has (`TableProperties.LargestIsExclusive`), and two files of a level may meet there without overlapping. A range where everything is deleted and nothing below needs a tombstone leaves no file. Output files end at `TargetFileSizeBase`, between two keys.
4. **Install.** One manifest save replaces the inputs with the outputs, and a new version replaces the family's version. A reader of an older version keeps reading the files of that version. A file that leaves the manifest is deleted when the last version that lists it closes, possibly on the thread of the last reader to leave it.

Compactions that run at once keep out of each other's way, as RocksDB's picker: a file that a running compaction reads is not picked again (RocksDB's `being_compacted`); a family has one level 0 compaction at a time, since level 0's files overlap; a merge of level 0 waits while a file of the base level in its range is in a running compaction; and a compaction into a level waits while a running compaction into that level writes an overlapping range (RocksDB's `RangeOverlapWithCompaction`), so their outputs never overlap. The scores leave out the files that run. So for each key, the versions in a level stay newer than those below: a merge into a level holds every file of that level in its range, and no other compaction can move a version of those keys past it. Each compaction installs on its own, in one manifest save under the state lock, into the version that the others' installs left. After a compaction failure, no other compaction installs; a merge that ends after it deletes its outputs.

`DeleteFilesInRange` drops, in one manifest save, the files of levels 1 to 6 whose keys all lie in a range, and leaves level 0, the memtables, and the files of a compaction that runs. As in RocksDB, it ignores sequence numbers: a key of a dropped file is gone for later reads even when no delete was written for it, while reads and iterators that started before still see it, and an older version of a key in a lower file that reaches past the range can come back. A dropped file is deleted when no reader uses it any more. Kommander reclaims a Raft log's dead prefix this way, with no rewrite: one partition's files do not overlap, so they move down whole, and each one is dropped once its last entry is below the compaction floor.

A crash before the manifest save leaves the outputs as orphans, and a crash after it leaves the inputs as orphans; the next open deletes them. `CompactRange` compacts the range one level after the other, as RocksDB's manual compaction: level 0's files in the range into the base level, then each level from the base level to level 5 into the one below, on the same thread, and returns when the last is installed. So a delete in the range reaches the bottom and drops what it hides. As in RocksDB with no compaction filter, level 6 files alone are not rewritten. A manual compaction runs alone, as RocksDB's default `exclusive_manual_compaction`: while one waits, no automatic compaction starts, and each of its steps waits until no other compaction runs. `Dispose` stops a merge that runs and deletes what it wrote. A compaction failure, like a flush failure, stops all later writes until the database is opened again.

## Pacing background writes

A table reaches its file through a 1 MiB buffer, as RocksDB's `WritableFileWriter` with its default `writable_file_max_buffer_size`: one write a megabyte rather than two a block. Before each write of a flush or a compaction, the builder asks the `RateLimiter`, if the database has one, for those bytes, at high priority for a flush and low for a compaction, as RocksDB's `GenericRateLimiter`: each refill period, 100 ms by default, hands out the rate times the period, to the flushes first and on every tenth refill to the compactions first, and a write that finds it spent waits for the next one. A write larger than a period's budget asks in pieces. An auto-tuned limiter starts at half its rate and moves between a twentieth of it and all of it, as RocksDB's `auto_tuned`, by how often the writes waited. WAL writes, the manifest, a replay's flushes and checkpoints are not paced.

After every `BytesPerSync` bytes of a table (1 MiB once a `RateLimiter` is set), the builder starts the writeback of what it wrote, `IStorageFile.SyncRange`, `sync_file_range(SYNC_FILE_RANGE_WRITE)` on Linux, so the table reaches the drive as it is written instead of all at its last sync. On a drive that commits synced writes slowly, that last sync holds up the WAL's syncs of the same moment (see "Synced writes beside background writes" in [benchmarks.md](benchmarks.md)). A failed range sync fails the table's write, as RocksDB's `RangeSync` does.

## Write stalls

When flushes add level 0 files faster than compaction removes them, writes slow down and then stop, as in RocksDB. The condition is database-wide: one family past a trigger holds back the writes to every family. Files that a compaction is reading count.

- **Delay.** While a family's level 0 holds `Level0SlowdownWritesTrigger` files, each WAL leader, before it appends its group, takes credit from a bucket that refills at `DelayedWriteRate` once a millisecond, and pays for the bytes of the group before it, as RocksDB's write controller. With too little credit, it sleeps without the state lock, in steps of 1 ms, until the rate pays for those bytes or the delay ends. The writers behind it queue meanwhile.
- **Stop.** While a family's level 0 holds `Level0StopWritesTrigger` files, the leader waits until a flush or a compaction install brings every family below the trigger. A flush or compaction failure, or `Dispose`, fails the waiting group instead. Flushes still run during a stop, so level 0 can grow past the stop trigger.
- A family with `DisableAutoCompactions` stalls nothing, as in RocksDB: no compaction would end its stall. The memtable count stalls writes on its own: a switch waits for a flush when a family holds `MaxWriteBufferNumber` memtables.

## SSTables

An SSTable stores internal keys: the user key, the sequence number, and the kind. So a read orders the versions of a key, and the range tombstones over it, across the memtables and the tables by sequence number. It holds 4 KB data blocks, each stored raw or, with `ColumnFamilyOptions.Compression`, as an LZ4 block when that saves at least an eighth of it, a range tombstone block, the partitions of its index and filter, a properties block, a top-level index, and a footer. Every block and the footer carry a CRC-32. The index holds the last internal key of each data block, cut into partitions of about 4 KB of index entries, as RocksDB's partitioned index; each partition has a Bloom filter on the user keys of its blocks (10 bits per key), and the top-level index holds the last internal key of each partition and the handles of its index and filter. A table written before partitions (version 3 or 2) has one index and one filter, read as one partition. `TableFormat` in `Engine/TableFormat.cs` documents the exact layout.

An open table keeps its range tombstones and its top-level index in memory, and its index and filter partitions, which lookups need, either in memory or in a block cache. A lookup searches the top-level index for the partition whose last key is at or after its key, checks that partition's filter, and searches the partition's index for the block. The reader decodes each index into one array of the last keys laid end to end, one of where each starts, and one each of their sequence numbers, offsets and sizes, so an index is five objects however many blocks it has; one array per key made a long-lived object for every 4 KB of data, 25 million of them per 100 GB. The partitions take about 2% of the table's bytes, and twice that with LZ4, which shrinks the data but not the keys; the top-level index about 0.04%.

With `ColumnFamilyOptions.CacheDataBlocks`, a family's `BlockCache` also holds the data blocks its reads take from the tables: a read of a block looks it up in the cache, keyed by the database's owner number, the table's number and the block's offset, and a miss reads, verifies and decompresses the block from the file, then caches its entries as one array unless `ReadOptions.FillCache` is false. A read of a cached block makes no system call and decompresses nothing. `Get`, the rounds of `MultiGet`, where a cached block settles its keys without joining the round's `MultiRead`, and iterators all take blocks from the cache; compactions read with `FillCache` off, so a compaction's inputs do not push the readers' blocks out. A table that a compaction retires leaves its data blocks to the LRU, as RocksDB does: its number is never read again, and finding its blocks would take its whole index. A database that closes erases every entry under its owner number, in one pass over each shard. It is off by default: each lookup of a cached block takes a shard's lock, and each block a miss caches is an array that lives until the cache evicts it, which from 8 reader threads, or on a store much larger than the cache, made reads slower than the page cache alone (see [benchmarks.md](benchmarks.md)).

With `ColumnFamilyOptions.CacheIndexAndFilterBlocks`, a table puts each partition's index and filter in the family's `BlockCache` as one entry when it opens, keyed by the database's owner number, the table's number and the partition, and keeps only its top-level index. A lookup takes its partition from the cache, under the lock of one of its shards, and a miss reads and verifies the partition's two blocks from the file again, a few kilobytes, and caches them unless `ReadOptions.FillCache` is false. The cache is an LRU of a byte capacity, split into shards; it evicts the least recently used entries that nothing pins, and stays over its capacity when only pins are left. As RocksDB's LRU cache, each shard's order is two lists: a high-priority pool of up to `HighPriorityPoolRatio` of the shard (0.5) for the index and filter partitions and every entry read again since its insert, and a low-priority pool for the rest. An entry that overflows the high-priority pool moves to the newest end of the low one, so the two stay one LRU order, and an eviction takes from the low pool first: the blocks of a scan, each read once, evict one another and not the indexes or the blocks read often. A reader that took an index keeps it after an eviction: the blocks of a table never change, and the garbage collector frees them after the last reader, so a read holds no reference in the cache. With `PinL0FilterAndIndexBlocksInCache`, a level 0 table pins its partitions until a move takes the table out of level 0, as every lookup searches every level 0 table. A table that closes erases its partitions, and a database that closes erases its data blocks too, so a cache shared by several databases holds nothing of a closed one. A `WriteBufferManager` created with the cache charges the memtables to it as pinned entries of 256 KiB, so one capacity bounds both.

## Checkpoints

`CreateCheckpoint` writes a copy of the database to a new directory, as of one sequence number in every column family. Under the state lock, where every memtable switch, flush install and compaction install happens, it reads the latest published sequence number and counts itself into the current version of each family, so the tables of those versions stay open and their files stay in place, whatever flushes and compactions do next. Outside the lock, it writes, for each family, a level 0 table from each memtable of the version with what a read at that sequence number sees of it (the entries at or below the number, newest version of each key first, and the range tombstones at or below it), then links the version's tables of every level into the copy under their own numbers and levels. A table file is never written after a manifest names it, and a delete removes only one name, so the copy and the source share the file safely; when the file system refuses a link (`IStorageEnvironment.TryLinkFile` returns false, across file systems or on one without hard links), the checkpoint copies that table and every later one. The memtables take writes meanwhile; their newer entries are above the number and stay out. The copy's manifest lists those tables, no WAL file, and every family as flushed up to the sequence number, so it opens with nothing to replay and numbers its own writes past that. The manifest's save flushes the directory, and `FORMAT`, written after it, is the last file, so a directory that lacks it holds an unfinished copy, and `Open` refuses it. A failure deletes the files written; it does not stop the source's writes.

The check that the directory does not exist comes first, and its creation later, so another checkpoint or an `Open` can take the directory between them. So the checkpoint takes the directory's `LOCK`, as `Open` does, and goes on only when the directory holds nothing else; it keeps the lock until the copy is complete or deleted, and the copy keeps the `LOCK` file. A checkpoint that loses the directory fails without touching a file in it.

`Dispose` tells a running checkpoint to stop, and waits for it before it closes the tables the checkpoint reads. The checkpoint checks before each file and link, between the chunks of a table it copies, and before `MANIFEST` and `FORMAT`; a check that finds the database closing deletes what the copy wrote and fails with `ObjectDisposedException`. A checkpoint past its check before `FORMAT` completes, and `Dispose` returns after it.

## Files in the data directory

| File | Content |
| --- | --- |
| `LOCK` | An exclusive lock. Only one open database can use the directory. |
| `FORMAT` | The format version, `solarium-format 5`. A format-2, format-3 or format-4 directory moves to format 5 at open: format 3 differs from 2 in new WAL files only, format 4 from 3 in new SSTables only (table version 3, whose data blocks have a type and may be compressed), and format 5 from 4 in new SSTables only (table version 4, whose index and filter are partitioned), so its WAL files still replay and its version 3 and 2 tables still read until a compaction rewrites them. A format-1 directory is migrated at open. |
| `MANIFEST` | The live WAL files, the column families, their SSTables with the level of each, and the flush point of each family. A binary record with a CRC-32, replaced atomically. `Manifest` in `Engine/Manifest.cs` documents the layout. Version 3, which adds levels 1 to 5 and a flag per table; a version 2 or 1 manifest still loads. A first open writes it after `FORMAT` and before any WAL or SST file, so `Open` takes a directory without it as new only when it holds nothing but `LOCK`, `FORMAT` and temporary files; it refuses one with any other file, whose manifest was lost, without changing anything in it. |
| `NNNNNN.log` | A WAL file. |
| `NNNNNN.sst` | An SSTable. |
